# SPEC 0001 - SYSTUTOR OSS Core v0.2 Persistencia Auth Tenancy RBAC

## Estado

Aprobada

## Contexto

La version inicial del core ya provee:

- estructura monorepo;
- app `FastAPI`;
- contrato base de plugins;
- health checks basicos;
- base documental para agentes.

Todavia falta convertir esa base en un core persistente y utilizable por futuros modulos.

El siguiente paso es implementar persistencia real, autenticacion basica, tenancy logico y RBAC minimo sin entrar todavia en modulos de negocio, migracion legacy ni integraciones externas.

## Objetivo

Implementar `SYSTUTOR OSS Core v0.2` con:

- persistencia del core;
- Alembic operativo;
- auth basica con JWT;
- hashing de password;
- tenancy por `tenant_id`;
- RBAC minimo funcional;
- auditoria persistente;
- event log persistente;
- seed inicial de demo;
- pruebas base del core.

## No objetivos

Queda fuera de alcance en esta iteracion:

- modulos de negocio completos;
- logistica funcional;
- migracion legacy;
- integracion con SQL Server;
- jobs reales con Dramatiq;
- runtime avanzado de plugins;
- RLS de PostgreSQL;
- multi-schema por tenant;
- integraciones frontend.

## Alcance

Toca:

- `apps/api`
- `docs/specs/core`
- `README.md`
- `.env.example`
- `plugins/logistics/plugin.json` si requiere ajuste de contrato

## Reglas de negocio

- el kernel no debe absorber logica de negocio de plugins;
- `tenant_id` se aplica en tablas donde corresponda;
- auth minima basada en email + password;
- permisos declarativos estilo `core.plugin.read`;
- claims iniciales derivados de `tenant_id` y `branch_id` del usuario;
- auditoria y eventos deben quedar persistidos;
- el core no debe escribir en SQL Server legacy;
- no se crean stored procedures ni triggers de negocio.

## Permisos

Permisos base esperados:

- `core.auth.me`
- `core.plugin.read`
- `core.plugin.manage`
- `core.audit.read`
- `core.event.read`
- `core.user.manage`
- `core.role.manage`
- `core.permission.manage`

## Eventos

Eventos minimos esperados:

- `core.user.logged_in`
- `core.user.login_failed`
- `core.plugin.discovered`
- `core.plugin.validated`

## Datos

Tablas del core esperadas:

- `tenants`
- `branches`
- `users`
- `roles`
- `permissions`
- `user_roles`
- `role_permissions`
- `audit_logs`
- `event_logs`
- `plugin_registry`

## Migraciones

Esta iteracion requiere:

- configuracion real de Alembic;
- migracion inicial del core.

## Auditoria y observabilidad

Debe registrarse como minimo:

- login exitoso;
- login fallido;
- accesos denegados relevantes;
- request_id;
- correlation_id;
- tenant_id y branch_id cuando aplique;
- eventos persistidos;
- auditoria persistida.

## Riesgos

- discrepancia entre entorno local y entorno de pruebas por driver PostgreSQL;
- complejidad innecesaria si auth/RBAC crece demasiado en esta fase;
- acoplar runtime de plugins al core persistente de forma prematura;
- crear modelos demasiado cerrados para futuras extensiones.

## Criterios de aceptacion

- existe configuracion real de SQLAlchemy 2.0 y Alembic;
- la migracion inicial crea todas las tablas del core;
- el seed crea tenant demo, branch demo, rol admin, permisos base y usuario admin;
- `POST /api/v1/auth/login` devuelve JWT en credenciales correctas;
- credenciales incorrectas devuelven error controlado;
- `GET /api/v1/auth/me` devuelve el usuario autenticado;
- la validacion de permiso devuelve `403` cuando corresponde;
- `audit_log` persiste registros;
- `event_log` persiste registros;
- el manifiesto del plugin existente se valida;
- las pruebas minimas del core pasan.

## Pruebas requeridas

- health check;
- ready check con DB;
- login correcto;
- login incorrecto;
- current user;
- validacion de permiso;
- escritura de audit log;
- escritura de event log;
- validacion de manifest.

## Notas para agentes

- leer `AGENTS.md` y ADRs relacionados antes de tocar codigo;
- mantener el kernel como infraestructura;
- no introducir dependencias nuevas salvo necesidad clara y justificada;
- no eliminar pruebas existentes;
- usar typing y testing alineados con Pyright, Ruff y Pytest.
