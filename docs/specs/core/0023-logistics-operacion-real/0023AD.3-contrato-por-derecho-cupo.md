# SPEC 0023AD.3 — Contrato por derecho/cupo de envases

## Estado

Vigente — 2026-07-22

> Esta spec reemplaza el enfoque de contrato visible desde cada bombona y redefine el modelo contractual como derecho/cupo por cliente + tipo de envase.
> `0023AD` y `0023AO` quedan como contexto histórico en todo lo que no contradiga este documento.

## Problema

Un contrato de envases no representa una lista fija de seriales.

En la operación real:

- hoy el cliente puede tener `00002..00100`;
- mañana puede tener `02000..02100`;
- ambos escenarios pueden pertenecer al mismo contrato activo.

Por tanto, modelar o exponer el contrato desde la ficha de una bombona como si esa bombona "tuviera su contrato" introduce una semántica falsa.

## Decisión de dominio

### 1. El contrato no vive dentro de la bombona

El contrato es un acuerdo comercial con el cliente.

Define:

- tipo de contrato;
- vigencia;
- cantidad comprometida;
- tipo de envase/producto;
- condiciones económicas;
- estado documental.

No define un conjunto fijo de seriales.

### 2. Los seriales concretos viven en posesión/custodia

Los seriales que el cliente tiene realmente en un momento dado se derivan de la operación:

- movimientos confirmados;
- custodia/ownership;
- estado actual del envase;
- ledger de posesión del cliente.

Eso es variable y no debe quedar modelado como si fuera parte estática del contrato.

### 3. El contrato expresa derecho/cupo, no amarre a cilindro fijo

Modelo correcto:

```text
contrato = derecho del cliente a N envases de un tipo/condición
seriales actuales = foto operativa variable
```

## Regla fuerte

```text
contrato != lista fija de seriales
```

## Consecuencias inmediatas

1. La UI de `Envases` no debe mostrar creación/gestión contractual desde la ficha de una bombona.
2. La navegación principal de `logistics` no debe tratar el submódulo contractual actual como flujo vigente hasta rediseñarlo.
3. La lectura correcta para comparar negocio vs realidad es:
   - `contracted`
   - `assigned` / posesión
   - `at_customer`
   - desvíos

## Modelo objetivo mínimo

### Contrato

Cabecera contractual por cliente:

- `customer_id`
- `contract_type`
- `start_date`
- `end_date`
- `status`
- `product_id` o tipo de envase
- `condition` cuando aplique
- `contracted_quantity`
- datos económicos/documentales

### Operación real

No en el contrato, sino en lectura derivada desde:

- `movements`
- `ownership`
- `customer possession ledger`
- `current_state`

## Eliminación / retiro de v1 actual

Se retira como feature vigente:

- acceso a contratos desde la ficha de `Envases`;
- acceso de navegación principal a la pantalla actual de contratos, mientras siga modelada con la semántica vieja.

Esto es retiro de runtime/UI, no borrado histórico del código o documentos.

## No objetivos

- no rediseñar hoy toda la persistencia contractual;
- no resolver firma digital en esta spec;
- no definir todavía facturación o cobro;
- no borrar la historia documental previa.

## Siguiente implementación esperada

La próxima iteración debe construir:

1. contrato por cliente + derecho/cupo;
2. resumen derivado de posesión real por producto/condición;
3. comparación clara entre `contracted` y `at_customer`;
4. sin amarre contractual visible por serial individual.
