# ADD Minimo - Llenado desde Criogenicos a Cilindros Resultado

## Contexto

La `SPEC 0040` implementada resuelve bien el caso donde:

- el producto del cilindro ya es el mismo producto que se descuenta del stock;
- el llenado solo mueve carga tecnica al propio cilindro;
- no hace falta distinguir `producto fuente` vs `producto resultado`.

Ese modelo no alcanza para envases criogenicos.

En esta operacion real del negocio ocurre otra cosa:

1. existe un stock fuente criogenico;
2. se usa ese stock fuente para llenar cilindros finales;
3. los cilindros llenos quedan almacenados y contados como otro producto resultado;
4. una vez transformado, ese contenido no vuelve al mismo criogenico.

Ademas, la verificacion directa sobre el legacy (`BasePro`) mostro que la transformacion no vive en una sola magnitud.

El legacy separa al menos tres datos distintos:

- `Formula.cantidad` -> consumo del producto fuente;
- `Edetalle_Producto_Bombona.M3_gas` -> gas equivalente del resultado;
- `Edetalle_Producto_Bombona.PESO_NETO_KG` -> peso neto del resultado.

Para LOX y LIN, `receta_mostrarxcod` expone `Formula.cantidad` en `Litros` del producto fuente.

Ejemplo real:

```text
stock fuente:
  OXIGENO LIQUIDO CRIOGENICO

resultado de la operacion:
  100 cilindros OXIGENO 200 BAR
```

## Frase guia

**El criogenico es la fuente a descontar. El cilindro final es el resultado a almacenar. Vaciar un cilindro no destransforma ese resultado al mismo criogenico.**

## Problema exacto

La regla actual de `0040` es:

```text
producto del cilindro = producto que se descuenta
```

Para criogenicos, la regla correcta es:

```text
producto resultado del cilindro != producto fuente a descontar
```

Por eso hace falta singularizar una arquitectura minima para este caso sin rehacer todavia todo `Envases`.

Tambien hace falta evitar una ambiguedad peligrosa:

```text
cantidad fuente consumida
!=
gas equivalente del resultado
```

Si el sistema colapsa ambas cosas en una sola columna o unidad, termina mezclando:

- stock del tanque criogenico;
- rendimiento gaseoso del producto final;
- peso neto del resultado.

## Decision minima de arquitectura

### 1. Dos productos distintos con roles distintos

En el llenado criogenico deben existir dos roles explicitos:

- `result_product_id` -> tipo de cilindro resultado al que pertenecen los seriales vacios preexistentes que se van a llenar;
- `source_product_id` -> producto criogenico del que se descuenta stock.

Regla fuerte:

```text
source_product_id = stock fuente a consumir
result_product_id = tipo estricto del cilindro serializado que se transforma a lleno
```

Y cada rol debe poder resolver metricas distintas:

- `source_product_id` -> `source_quantity_liters`
- `result_product_id` -> `result_m3_gas`, `result_net_weight_kg`

### 1.1. Metricas separadas por contrato

Para el caso criogenico, el contrato minimo no debe colapsar magnitudes.

Debe distinguir al menos:

- `source_quantity_liters` -> cuanto producto fuente sale del criogenico;
- `result_m3_gas` -> que volumen gaseoso equivalente representa el resultado;
- `result_net_weight_kg` -> que peso neto final declara el resultado.

Ejemplo real verificado en legacy:

```text
Oxigeno Industrial B10 / 300BAR
source_product_id = Oxigeno Liquido - LOX
source_quantity_liters = 3.798
result_m3_gas = 3.20
result_net_weight_kg = 3.80
```

### 2. El cilindro sigue naciendo tipado por su producto resultado

No se cambia la identidad base del cilindro.

El `product_id` del cilindro sigue representando el resultado operativo con el que ese serial quedara almacenado, planificado y despachado.

Ejemplo:

```text
cilindro serial X
product_id = OXIGENO 200 BAR B50
```

Eso no significa que el stock a descontar sea ese mismo SKU.

Tampoco significa que el llenado cree un envase nuevo.

Regla fuerte de este caso:

```text
el cilindro ya existe vacio
el llenado solo cambia su estado material a lleno
```

### 3. El llenado criogenico es una transformacion unidireccional

El flujo correcto queda asi:

```text
stock fuente criogenico
-> operacion de llenado
-> seriales vacios preexistentes del tipo correcto
-> esos seriales quedan cargados
```

No se crea un nuevo producto resultado en el sentido de recrear el envase.

Lo que se transforma es el estado material de seriales ya existentes.

### 3.1. Capacidad y stock insuficiente

El sistema debe validar dos cosas antes de confirmar el llenado:

- que existan seriales vacios suficientes del tipo correcto;
- que exista stock fuente criogenico suficiente para la cantidad solicitada.

Caso real:

```text
quiero llenar 100 cilindros
pero el stock fuente solo alcanza para 60
```

Decision minima:

```text
el llenado parcial esta permitido
pero debe ser explicito y auditado
```

Eso significa que el sistema no debe simular exito total cuando solo pudo llenar una parte.

Debe quedar claro al menos:

- cantidad solicitada;
- cantidad realmente llenada;
- seriales efectivamente llenados;
- motivo del parcial si aplica.

### 3.2. Atomicidad obligatoria

El llenado criogenico no puede dejar estados intermedios inconsistentes.

Regla fuerte:

```text
descuento del criogenico fuente
+ cambio de estado/carga de seriales llenados
= una sola transaccion atomica
```

Riesgo prohibido:

```text
descuenta LOX
pero falla el cambio de los cilindros
```

Si una parte falla, toda la operacion debe revertirse.

### 3.3. Batch de llenado

Ademas del evento por cilindro, el sistema necesita un identificador comun de la operacion de llenado.

Pregunta que debe poder responderse despues:

```text
que lote u operacion de llenado genero estos cilindros?
```

Solucion minima de este slice:

- agregar `fill_operation_id` o equivalente comun a los eventos afectados;
- no es obligatorio definir todavia una tabla compleja, pero si una correlacion estable y auditable entre seriales de la misma corrida.

## Regla de receta obligatoria

No se puede llenar un cilindro criogenico sin receta definida para su `result_product_id`.

Regla fuerte:

```text
sin receta
-> no se llena
```

La receta minima debe resolver al menos:

- `source_product_id`;
- `source_quantity_liters`;
- `result_m3_gas`;
- `result_net_weight_kg`.

No existe flujo inverso automatico:

```text
cilindro vaciado
-> mismo criogenico origen
```

Eso queda explicitamente prohibido como comportamiento por default.

### 4. Vaciar no revierte la transformacion

`vaciar cilindro` en este caso sigue significando:

- quitar la carga actual del cilindro;
- dejarlo operativo como vacio;
- dejar traza auditada;
- **no** devolver stock al criogenico fuente.

Si el negocio algun dia necesita registrar recuperacion, merma, venteo o reproceso, eso sera otro flujo separado, no una consecuencia implicita de `vaciar`.

### 5. La configuracion por default vive en el producto resultado

Para no obligar a elegir manualmente la fuente en cada llenado criogenico, el sistema debe poder resolver una configuracion por default del producto resultado:

```text
OXIGENO 200 BAR B50
  -> descuenta por default de OXIGENO LIQUIDO CRIOGENICO
```

Ese mapeo no redefine el producto del cilindro.

Solo define:

```text
de que stock fuente se descuenta cuando se llena este resultado
```

## Owners

### `Envases`

Owner de:

- serial fisico;
- pertenencia estricta del serial a su `result_product_id`;
- estado actual del cilindro;
- carga tecnica actual;
- trazabilidad de llenado/vaciado.

### `Productos`

Owner de:

- producto resultado del cilindro;
- producto fuente criogenico asociado por default;
- receta y metricas tecnicas del resultado (`source_quantity_liters`, `result_m3_gas`, `result_net_weight_kg`).

### `Stock`

Owner de:

- descuento del producto fuente en su unidad real de consumo;
- auditoria de entradas/salidas agregadas.

En este slice no se asume automaticamente un alta de `stk_balance` agregado del resultado al llenar.

El resultado operativo minimo puede resolverse dejando seriales preexistentes del tipo correcto como llenos.

## Invariantes minimos

1. Un llenado criogenico siempre descuenta stock del `source_product_id`.
2. El cilindro final sigue ligado al `result_product_id`.
3. `source_product_id` y `result_product_id` pueden ser distintos y esa diferencia es valida.
4. `source_quantity_liters` no debe confundirse con `result_m3_gas`.
5. `result_m3_gas` no reemplaza a `result_net_weight_kg`; ambas metricas pueden coexistir.
6. El llenado criogenico no crea un envase nuevo; toma seriales vacios preexistentes del tipo correcto y los deja llenos.
7. Si no alcanza el stock fuente o no alcanzan los seriales vacios, el sistema no debe declarar exito total; el parcial debe quedar explicito y auditado.
8. El llenado criogenico debe ser transaccion atomica entre descuento de fuente y transformacion de seriales.
9. Cada corrida de llenado debe poder agruparse por `fill_operation_id` o equivalente comun.
10. Sin receta definida para el `result_product_id`, el llenado debe rechazarse.
11. Vaciar un cilindro no devuelve stock al mismo criogenico por default.
12. El sistema no debe inferir que un cilindro vacio implica recuperacion del contenido fuente.
13. La transformacion debe ser auditable como operacion distinta del llenado simple de `0040`.

## Alcance de este ADD minimo

Este ADD solo fija la decision arquitectonica minima:

1. distinguir producto fuente vs producto resultado;
2. distinguir cantidad fuente en litros vs metricas del resultado;
3. fijar que el resultado se materializa sobre seriales vacios preexistentes del tipo correcto;
4. declarar si la operacion fue total o parcial con trazabilidad explicita;
5. exigir atomicidad entre descuento de fuente y actualizacion de seriales;
6. exigir correlacion comun por `fill_operation_id` o equivalente;
7. declarar la transformacion como unidireccional;
8. prohibir la reversion automatica al mismo criogenico;
9. preparar un mapeo por default desde producto resultado hacia producto fuente.

## No objetivos todavia

- no definir aun el contrato API final;
- no definir aun mermas, evaporacion o boil-off;
- no decidir aun si en una etapa posterior conviene reflejar tambien el resultado en `stk_balance` agregado ademas del serial;
- no modelar aun reproceso o recuperacion parcial.

## Evidencia legacy ya fijada

La parte metrologica minima ya no esta abierta en abstracto.

Tomando como referencia el legacy:

1. `Formula.cantidad` representa consumo fuente;
2. para LOX/LIN el legacy lo expone en `Litros`;
3. `Edetalle_Producto_Bombona.M3_gas` representa el gas equivalente del resultado;
4. `Edetalle_Producto_Bombona.PESO_NETO_KG` representa el peso neto del resultado.

Este ADD todavia no define el endpoint final, pero si fija que la futura implementacion no debe volver a colapsar estas tres magnitudes en una sola columna ambigua.

Archivo de referencia extraido desde la base legacy:

- `formulas_criogenicas_legacy_real.csv`

## Pregunta singular que este ADD responde

```text
cuando lleno cilindros desde un criogenico,
que producto se descuenta y que producto queda almacenado?
```

Respuesta:

```text
se descuenta el producto fuente criogenico
y se llenan seriales preexistentes del producto resultado
```

Y ademas:

```text
el tanque criogenico pierde litros fuente
y el resultado conserva su propio M3_gas y peso neto
```

## Encaje con 0040

`0040` sigue vigente para cilindros donde el producto del envase y el stock a descontar coinciden.

Este ADD no la invalida.

Solo abre una rama arquitectonica minima para el caso donde el llenado es en realidad una transformacion:

```text
source_product_id -> result_product_id
```
